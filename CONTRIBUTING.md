# Contributing and governance

This document is the governance record for OpenFAWE. It names the maintainer and defines the
contribution, review, dependency and deprecation rules.

**Maintainer:** Yinong Tian ([ORCID 0000-0003-1912-0232](https://orcid.org/0000-0003-1912-0232)),
CENTEC, Instituto Superior Técnico, University of Lisbon.
The maintainer is responsible for release approval and for the provenance review described in §5.

---

## 1. Current state

OpenFAWE is at **v0.1.0 — specification and roadmap**. There is no production solver yet, so there is
not yet a code contribution path in the usual sense.

What *is* useful right now:

- **Corrections and challenges to the specification.** If the design basis, the evidence policy or the
  acceptance thresholds look wrong, unachievable or self-serving, open an issue. A specification that
  survives being argued with before implementation is worth more than one that does not.
- **Comparator and benchmark suggestions.** Pointers to published cases, experimental datasets or
  field records that could serve as verification or component-validation comparators are especially
  welcome — see [`docs/evidence-policy.md`](docs/evidence-policy.md) §1.
- **Interface requirements.** If you would want to drive OpenFAWE from another toolchain, say so
  before the interfaces freeze rather than after.

## 2. Issues

Use [GitHub Issues](https://github.com/robytian/OpenFAWE/issues). Please include:

- which document or component the issue concerns;
- what you expected and what is written or produced instead;
- for a numerical issue, the versioned case identifier (see
  [`docs/architecture.md`](docs/architecture.md) §4) — without it a result cannot be reproduced and
  the issue cannot be closed properly.

Issues that report a defect in a released result are handled in public. A result that cannot be
regenerated from its archived case identifier is **withdrawn**, not footnoted.

## 3. Pull requests (once code lands)

1. Open an issue first for anything beyond a typo, so the scope is agreed before work starts.
2. One logical change per pull request.
3. New or changed numerical behaviour requires a regression test and a note on which evidence class
   it falls into (verification or component validation — never both).
4. Continuous integration and the existing test suite must pass.
5. Documentation is part of the change, not a follow-up.
6. The maintainer reviews and approves every merge into the release branch.

**Inbound = outbound.** Contributions to project-owned code are accepted under
[Apache-2.0](LICENSE); contributions to documentation and benchmark data under CC BY 4.0. By opening
a pull request you confirm you have the right to contribute the material under those terms.

**Do not contribute:** code copied from an incompatible licence; restricted, partner-confidential or
unpublished third-party data; or material generated by submitting confidential inputs to an external
service.

## 4. Dependency review

Every proposed dependency is reviewed against four questions, and the answers are recorded in the
pull request:

| Question | Why it matters |
|---|---|
| What is its licence, and is it compatible with Apache-2.0 redistribution? | Release blocker if not |
| Is it *called through an adapter*, or would it be vendored? | OpenFAWE does not vendor third-party solvers |
| Is it maintained, and is there a fallback if it is abandoned? | Reproducibility of archived releases |
| Does it need network access or external services at runtime? | Restricted inputs must never leave the local environment |

A dependency that cannot be pinned to an exact version does not enter a release.

## 5. Provenance review at release

Before any tagged release the maintainer confirms, in writing in the release notes:

- no MRUT source is imported, linked, called or vendored (see
  [`docs/architecture.md`](docs/architecture.md) §5);
- every third-party component is present by adapter, with its licence recorded;
- no restricted or partner-confidential input is present in the repository or the archive;
- every released numerical result carries a resolvable versioned case identifier;
- every cost statement carries its computed/assumed split and its stability label.

Continuous integration and automated tests support this review; they do not replace it. The final
check is a human one.

## 6. Deprecation

- Deprecations are announced in [`CHANGELOG.md`](CHANGELOG.md) at least **one minor release** before
  removal, with the replacement named.
- A deprecated interface keeps working, with a warning, for that whole period.
- Removals happen only at a minor or major version boundary, never in a patch release.
- **Archived releases are never modified.** If a released result is found to be wrong, a new version
  is published that says so, and the archived record is annotated — the original is not silently
  replaced.

## 7. Versioning and releases

- [Semantic versioning](https://semver.org/) applies from the first code release.
- Each tagged release carries locked environment specifications and container recipes
  (Docker / Apptainer) so archived results remain executable.
- Each release is archived on Zenodo under the concept DOI
  [10.5281/zenodo.21656345](https://doi.org/10.5281/zenodo.21656345) and exposed through OpenAIRE.
- Release notes state what changed, what was deprecated, and what evidence class each new or changed
  result falls into.

## 8. Conduct

Technical disagreement is welcome and expected; personal attacks are not. Reports of unacceptable
behaviour go to the maintainer, who may remove comments, close threads or block accounts. Discussion
of a released result is judged on the evidence, not on who raised it.
